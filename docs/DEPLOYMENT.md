# 🚀 دليل النشر (Deployment)

<div dir="rtl">

ثلاثة مسارات مدعومة رسمياً، من الأسهل للأقوى. افترض أن لديك نسخة من المستودع و Bun مثبتاً للتطوير.

## المسار 1 — Vercel + Neon (الأسرع لبدء التشغيل)

المخطط منذ v4.2 على PostgreSQL حصرياً — على Vercel اربطه بقاعدة Neon (المسار 3 للتهيئة):

1. هيّئ قاعدة Neon أولاً (ترحيلات + بذر) — أسهل طريق «زر من Actions» أدناه في قسم المسار 3.
2. اربط المستودع بـ [vercel.com](https://vercel.com) (New Project ← Import) — يُكتشف تلقائياً بلا vercel.json (Framework Preset: Next.js؛ لا تحذف `output: standalone` فالمنصة تتجاهله بأمان).
3. أضف متغيرات البيئة (Settings → Environment Variables — كلها للبيئات الثلاث Production/Preview/Development):
   ```
   DATABASE_URL="postgresql://…@ep-XXXX-pooler.REGION.aws.neon.tech/neondb?sslmode=require"   # المجمّعة
   DIRECT_URL="postgresql://…@ep-XXXX.REGION.aws.neon.tech/neondb?sslmode=require"           # المباشرة — للترحيلات
   AUTH_SECRET="<سلسلة عشوائية ≥32 حرفاً — openssl rand -hex 32>"                          # إلزامي: بلاه يرفض الإنتاج التشغيل (fail-closed)
   ```
   اختيارية حسب الحاجة:
   ```
   ZATCA_VAT_NUMBER="3000…"         # تفعيل الفاتورة الضريبية المبسطة (ZATCA)
   ZATCA_SELLER_NAME="صيدلية رُبى"   # اسم البائع على الفاتورة
   SENTRY_DSN / NEXT_PUBLIC_SENTRY_DSN   # مراقبة أخطاء — بلا مفاتيح لا يُهيأ شيء
   ```
   > لا تحتاج `NEON_API_KEY` على Vercel إطلاقاً — إنه مفتاح إدارة لإجراء الاختبارات المؤقتة فقط.
4. Deploy — وسيُبنى تلقائياً في كل دفعة إلى `main` (CI يحمي الجودة)، والترحيلات لا تُنفذ عند البناء (فقط عند زر Actions أو يدوياً — لا عجلة مخطط مع كل deploy).

## المسار 2 — VPS / Docker (موصى به للصيدليات — بيانات داخل الصيدلية)

PostgreSQL محلي داخل الـ compose — بيانات الصيدلية في وحدة تخزين دائمة `pg-data`:

```bash
git clone https://github.com/magedmorshed173-ai/ruba-pharmacy.git && cd ruba-pharmacy
export AUTH_SECRET="$(openssl rand -hex 32)"   # إلزامي — fail-closed بلا استثناء
docker compose up -d --build                    # postgres + ترحيلات + المنصة على :3000
```

- **أول إقلاع ذاتي التهيئة**: خدمة `db` تصبح جاهزة → `db-migrate` يطبق الترحيلات وينتهي → المنصة تقوم. صفر خطوات يدوية.
- بيانات تجريبية (اختياري — يبذّر مستخدمين ومخزوناً ومبيعات 30 يوماً): `docker compose run --rm seed` — **أنشئ مستخدميك الحقيقيين من واجهة الإعدادات فوراً**.
- الترقية لاحقاً: `git pull && docker compose up -d --build` — الترحيلات الجديدة تُطبق آلياً بنفس الآلية.
- بديل Neon بدل القاعدة المحلية: استبدل متغيري `DATABASE_URL`/`DIRECT_URL` في `docker-compose.yml` بسلسلتي Neon (الاستضافة عند مزود آخر، القاعدة سحابية).

### TLS تلقائي خلف Caddy (موصى به)

`Caddyfile`:
```
pharmacy.example.com {
  reverse_proxy ruba-pharmacy:3000
}
```
شغّل حاويات compose وCaddy على شبكة Docker واحدة — Caddy يدير الشهادات تلقائياً.

### النسخ الاحتياطي

PostgreSQL — نسخة SQL مضغوطة بحجم ثوانٍ:
```bash
docker compose exec db pg_dump -U ruba ruba | gzip > backup-$(date +%F).sql.gz
# الاستعادة:
gunzip -c backup-2026-01-01.sql.gz | docker compose exec -T db psql -U ruba ruba
```
كذلك نوفر نسخاً احتياطياً JSON من داخل المنصة: الإعدادات ← النسخ الاحتياطي.

## المسار 3 — Neon Postgres (v4.2 — الموصى به، مُطبّق في هذا المستودع)

المشروع رُحّل رسمياً إلى Neon Postgres — المخطط والسكربتات جاهزة:

1. أنشئ مشروعاً في [console.neon.tech](https://console.neon.tech) وانسخ السلسلتين (المجمّعة `-pooler` + المباشرة).

### التهيئة بنقرة زر من GitHub Actions (الموصى بها — v4.6.1)

بيئة التطوير المقيّدة شبكياً (أو أي جهاز بلا وصول لنطاقات Neon) تُتهيّا القاعدة من عدّاء GitHub — الأسرار في Secrets ولا شيء في الكود:

1. أضف سرّين في المستودع (Settings → Secrets and variables → Actions → New repository secret):
   - `NEON_DATABASE_URL` = السلسلة **المجمّعة** (تحتوي `-pooler`)
   - `NEON_DIRECT_URL` = السلسلة **المباشرة** (بلا `-pooler`)
2. تبويب **Actions ← «Neon DB Setup» ← Run workflow** واختر الوضع:
   | الوضع | الاستخدام | ماذا يفعل |
   |------|-----------|-----------|
   | `catalog` | **إنتاج حقيقي** | ترحيلات + كتالوج الدواء والسجل الوطني (بلا مبيعات وهمية) |
   | `full` | بيئة تجريبية كاملة | ترحيلات + مستخدمون/مخزون/مبيعات 30 يوماً + كتالوج |
   | `baseline` | قاعدة قائمة كانت تعمل بـ `db push` | تسجيل `0_init` ثم تطبيق الترحيلات الأحدث — لا يمس البيانات |
   | `migrate-only` | ترقية روتينية | تطبيق الترحيلات المعلقة فقط |
3. تنتهي الخطوة الأخيرة بـ **تحقق حي** يطبع عدد الجداول والعدّادات — انسخه من سجل التشغيل للتوثيق.

### التهيئة اليدوية (بديل الزر)

```bash
# .env محلي بالسلسلتين ثم:
bun run db:migrate:deploy          # قاعدة جديدة
bun scripts/seed.ts && bun scripts/seed-drugs.ts && bun scripts/seed-national.ts   # بذر كامل تجريبي
# أو لقاعدة قائمة بنمط db push:
bun run db:migrate:baseline        # ثم migrate deploy كما في الزر
```

### مزايا Neon للصيدليات

- تجميد تلقائي للـ compute عند الخمول (توفير تكلفة ساعات الإغلاق)
- فروع قواعد بيانات (branching): نسخة تجريبية معزولة لكل ترقية قبل تطبيقها
- استرجاع نقطة زمنية (PITR) — أقوى من نسخ ملف SQLite اليدوي

### الاختبارات الحية على فرع مؤقت (v4.3)

جناح E2E يعمل على **فرع Neon مؤقت** تُنشئه الحاضنة وتحذفه تلقائياً — عزل
تام عن قاعدة الإنتاج مع باريتي كامل مع المخطط الفعلي:

```bash
bun run build && bun run test:e2e   # يتطلب NEON_API_KEY في .env
```

- بديل يدوي بلا مفتاح: `E2E_DATABASE_URL` (+ `E2E_DIRECT_URL`) لقاعدة Postgres جاهزة
- في CI: أضف أسرار الريبو `NEON_API_KEY` + `NEON_PROJECT_ID` + `NEON_PARENT_DATABASE_URL` — وبدونها تتخطى الخطوة بلطف
- تنظيف فروع الاختبار اليتيمة إن وجدت: `bun scripts/neon-clean-branches.ts`

### للمطورين المحليين (اختياري)

المخطط `postgresql` حصرياً منذ v4.2 — صيغة `file:` لم تعد صالحة لعميل Prisma. للتطوير بلا إنترنت شغّل Postgres محلياً بأسرع طريق: `export AUTH_SECRET="$(openssl rand -hex 32)" && docker compose up db db-migrate -d` ثم وجّه `DATABASE_URL`/`DIRECT_URL` في `.env` إليه — أو استخدم Neon مباشرة (التوصية الرسمية حتى محلياً، والطبقة المجانية كافية للتطوير).

## قائمة فحص ما قبل الإنتاج ☑️

- [ ] تغيير كلمات مرور حسابات البذرة الثلاثة فوراً (المستخدمون ← كلمة المرور)
- [ ] `DATABASE_URL` يشير لقاعدة دائمة (وليس `/tmp`)
- [ ] HTTPS مفعل (كوكي المصادقة `Secure` لن يعمل بدونه على النطاقات)
- [ ] نسخ احتياطي مجدول ومُختبَر (استعادة فعلية مرة واحدة!)
- [ ] مراقبة سجلات الحاوية/الخادم
- [ ] `NEXT_TELEMETRY_DISABLED=1` إن رغبت بتعطيل التتبع

## الترقيات

```bash
git pull && docker compose up -d --build
```
سجل التغييرات لكل إصدار في `CHANGELOG.md` — راجعه قبل الترقية.

## ترحيلات Prisma — خط الأساس 0_init (v4.4.1)

المشروع كان يعمل بنمط `db push` (بلا تاريخ ترحيلات) — أُنشئ الترحيل الأولي
`prisma/migrations/0_init/migration.sql` من المخطط الحالي، وقد وُثّقت صلاحته
بتنفيذه كاملاً في PostgreSQL (WASM/PGlite) وأنشأ 22 جدولاً بنجاح.

### على قاعدة Neon الحالية (البيانات موجودة — لا تُنفَّذ، تُسجَّل فقط)

```bash
# تأكد أن .env يضم DATABASE_URL (المجمّع) وDIRECT_URL (المباشر، بلا -pooler)
bun run db:migrate:baseline   # يسجّل 0_init كمُطبَّق — صفر لمس للبيانات
bunx prisma migrate status    # يجب: "Database schema is up to date!"
```

### على قاعدة جديدة (فرع Neon للمطوّرين، بيئة اختبار، ...)

```bash
bun run db:migrate:deploy     # ينفّذ الترحيلات بالترتيب
bun run scripts/seed.ts       # ثم البذر: users/categories/interactions
bun run scripts/seed-national.ts
bun run scripts/seed-drugs.ts
```

### قبل كل تغيير مخطط لاحق

استخدم `bunx prisma migrate dev --name <وصف>` بدل `db push` — فيولّد
ترحيلاً مرقّماً قابلاً للمراجعة والرجوع. أما `db push` فيبقى للاختبار
السريع على قاعدة محلية مؤقتة فقط.

التحقق من صحة أي ترحيل جديد بلا قاعدة حية:
`bun run db:verify-migration` (ينفّذه في PGlite ثم ينظّف الاعتماد تلقائياً)

## ZATCA والتحقق بخطوتين — v4.5

**الفاتورة الضريبية المبسطة (QR):** أضف الرقم الضريبي (15 رقماً) إلى البيئة
فيتولّد تلقائياً مع كل بيع: رقم تسلسلي `INV-<سنة>-<تسلسل>` + ضريبة 15%
شاملة + رمز QR بترميز TLV على الإيصال. بلا الرقم يستمر البيع طبيعياً
وتُحسب الضريبة في التقارير فقط.

**الترقيم التسلسلي:** جدول `InvoiceCounter` يزيد ذرياً داخل معاملة البيع —
لا فراغات ولا تكرارات حتى مع تزامن نقاط البيع.

**التحقق بخطوتين (TOTP):** كل مستخدم يفعّله من الإعدادات (QR → كود تأكيد).
المدير يُوجَّه لتفعيله عند الدخول. التعطيل يستلزم كوداً صحيحاً — كلمة
المرور المسروقة وحدها لا تصلح.

**CI:** `.github/workflows/ci.yml` — lint + tsc + 243 اختباراً + بناء
على كل ضغطة وطلب دمج + جناح Playwright على Postgres خدمي؛ الفشل يمنع الدمج.
و`neon-migrate.yml` — تهيئة/ترقية قاعدة Neon بنقرة زر (أعلاه).

## التأمين المالي وتعدد الفروع وPlaywright وSentry — v4.6

**التأمين الطبي:** لا يحتاج أي متغيرات بيئة — يعمل فوراً من الواجهات:
1. الإعدادات → «شركات التأمين»: أضف شركات التعامل (مدير فقط).
2. المرضى → زر الدرع الأخضر لكل مريض → أضف بوليصاته (رقم، تغطية %، مشاركة
   ثابتة اختيارية، تاريخ انتهاء).
3. نقطة البيع: اختر المريض ثم «تأمين» ثم البوليصة — يظهر تقسيم
   «حصة المؤمن / حصة المريض» قبل الإتمام، وتُفتح مطالبة تلقائياً.
4. التقارير → تبويب «التأمين»: مراجعة المطالبات؛ الاعتماد والرفض والتحصيل
   (مدير فقط) عبر آلة حالات صارمة — «محصّلة» نهائية بلا رجوع.

قواعد التقسيم: المشاركة الثابتة على المريض أولاً ثم نسبة التغطية على
المتبقي، وحصة المؤمن تُقرَّب لأسفل (floor) — المريض يتحمل كسور الهللات،
والجمع مضمون: `insurerAmount + patientAmount = netAmount` دائماً.

**تعدد الفروع:** الإعدادات → «الفروع» لإضافة الفروع، ثم تبويب المستخدمين
لتعيين فرع كل موظف. كل فاتورة تُسجَّل على فرع موظفها تلقائياً، وتقرير
المبيعات يُفلتر بالفرع. قرار معماري واضح: **المخزون مركزي واحد** في v4.6 —
تحويل المخزون بين الفروع مسار مستقبلي مستقل لا يُرتجل.

**CSP بـ nonce:** انتقلت من next.config إلى `src/middleware.ts` — nonce
لكل طلب + `strict-dynamic` وبلا `unsafe-inline` للسكربتات. لا ضبط مطلوب.
ملاحظة: الصفحة الجذرية `force-dynamic` (ضروري لحقن الـ nonce — الصفحة
الثابتة لا تستطيعه). إن أضفت صفحات جديدة ثابتة ستفتحها بلا nonce — اجعلها
ديناميكية أو أضفها لمستثنيات matcher بعد قياس أثرها.

**Playwright E2E:** `bun run test:playwright` — يعيد استخدامه في CI تلقائياً
على Postgres خدمي حقيقي (مهمة `e2e` في ci.yml). تشغيل محلي كامل يتطلب
قاعدة حية و`E2E_ADMIN_USER`/`E2E_ADMIN_PASSWORD` وبيان بذر مدير:
`bun scripts/seed-e2e.ts`. بلا بيانات تُنفَّذ اختبارات السطح العام فقط
ولا تفشل البقية إلا بوجود قاعدة — البيان `test.skip` مقصود.

**Sentry (اختياري):** أضف `SENTRY_DSN` (خادم) و`NEXT_PUBLIC_SENTRY_DSN`
(متصفح) إلى البيئة فقط — لا كود ولا حزمة إضافية مطلوبة؛ بلا مفاتيح لا
يُهيأ شيء إطلاقاً. معدل التتبع الافتراضي 10% (`SENTRY_TRACES_SAMPLE_RATE`).

**التقارير المجدولة (v5.1):** تعمل فوراً بلا أي متغيرات — كرون واحد يومي
00:00 بتوقيت السعودية (`vercel.json`) يولّد اللقطة اليومية دائماً، والأسبوعية
أول الاثنين، والشهرية أول الشهر (سلسلة تواريخ من نقطة واحدة — ضمن حد Hobby
في Vercel). متغيران اختياريان للتشديد والبريد:

- `CRON_SECRET` (شدّة إضافية موصى بها): عند ضبطه في Vercel يُلزم النقطة
  `POST /api/reports/snapshot` برأس `Authorization: Bearer <CRON_SECRET>` من
  الكرون، ويتحول التشغيل اليدوي إلى جلسة مدير حصراً. بلا ضبطه تعمل النقطة
  بوضع كرون مفتوح مقيّد 10 طلبات/دقيقة لكل IP وتكتب تجميعات محسوبة فقط
  (لا بيانات حساسة ولا تسريب).
- البريد عبر Resend (اختياري): `RESEND_API_KEY` + `REPORT_EMAIL_TO`
  (مستقبلون مفصولون بفواصل) و`REPORT_EMAIL_FROM` (اختياري) — يُرسل ملخص
  عربي RTL بعد كل لقطة يومية ناجحة. بلا المفتاحين لا يُرسل شيء إطلاقاً
  ولا يتأثر التوليد.
- التصدير إلى Excel: زر «تصدير Excel» في تبويب التقارير المجدولة يُنزّل
  XLSX حقيقياً (ورقتان: اللقطات وأعلى الأصناف) مبني داخلياً بلا مكتبات —
  الأوراق RTL والنصوص العربية سليمة.
